# Changing the site

Two kinds of change, with very different blast radius.

## Changing how it looks — no database work

Colours, fonts, spacing, section order, new layouts, different navigation,
adding an animation. All of it lives in:

```
templates/public/*.html     structure
assets/css/styles.css       styling
assets/js/main.js           behaviour
```

Edit, run `python3 build.py`, done. The database only supplies the words and
the image paths; how they are arranged is entirely template-side, so none of
this touches Supabase, `schema.js` or the admin panel.

Two rules worth keeping:

- Image fields must go through the filter: `{{ x.image|media }}`, never
  `/{{ x.image }}`. Uploaded images are absolute Supabase Storage URLs, and a
  hardcoded slash turns them into `/https://...` and breaks them.
- Keep the `.html` filenames. Routes are real filenames on the static host, and
  `main.js` highlights the active nav link by comparing the last path segment.

## Adding a new content field — five places

Say you want a video URL on each project. The data has to exist end to end, so:

**1. Supabase** — SQL Editor:

```sql
alter table public.projects add column video_url text default '' not null;
```

**2. `app/db.py`** — add the same column to the `projects` `CREATE TABLE`.
Skipping this is the trap: `sync.py` copies only columns the local SQLite table
already has, so a new Postgres column is silently dropped and the field appears
empty on the built site with no error anywhere.

**3. `app/views.py`** — add `"video_url"` to that section's `fields` list in
`SECTIONS`.

**4. Regenerate the admin's field map:**

```
python3 tools/gen_admin_schema.py
```

`admin/schema.js` is generated from `app/views.py` precisely so the two cannot
drift. Never edit it by hand.

**5. Use it** in `templates/public/project.html`.

Then `python3 build.py` and publish.

## Adding a whole new section

Same five steps, plus a `create table` in Supabase and matching RLS policies —
copy the pattern from `supabase/policies.sql`, which is generated by
`tools/gen_supabase_schema.py`. Without a policy the table is invisible to the
anon key and the build renders nothing.

## The generators

| Script | Produces | When to run |
|---|---|---|
| `tools/gen_admin_schema.py` | `admin/schema.js` | after changing `SECTIONS`, `SETTING_GROUPS` or `SEO_GROUPS` |
| `tools/gen_supabase_schema.py` | `supabase/schema.sql` | to re-export the whole schema and content from `data/site.db` |

Both are deterministic — running them twice gives the same file.

## Checking a change before publishing

```
python3 build.py --no-sync     # render from local SQLite, skip the Supabase pull
```

Then open `dist/index.html` in a browser. `--no-sync` matters when you are
iterating on templates: without it every build re-downloads from Supabase and
overwrites your local database.
